# GT Sync — v1.1 Design (GUI polish and automation)

(c)Copyright 2026 by Gennaro Eduardo Tangari.

Date: 2026-11-23 · Status: **approved by the author in conversation** (all items in one pull request) · Companion to `2026-11-23-gtsync-design.md` and `2026-11-23-gtsync-gui-design.md`

## 1. Intent

Make a running sync *legible* for someone who follows it closely, make wasted space *visible and motivating*, and let GT Sync work by itself without ever giving up the safety rules (merge only, nothing overwritten, deletions only through the review queue).

## 2. Scope

1. **Live sync stage** — replaces the progress sheet. The roots are shown as glass cards; the file being processed travels from its source card to its destination card; a log lists the latest operations with a verb, a name and the folders involved. It must not look like a classic file-copy dialog: no single percentage bar as the main element, no "x of y" wall of text. Honors Reduce Motion (the travel animation becomes a static highlight).
2. **Reclaimable space** — a big animated counter ("You can free 14.2 GB") from the exact-content duplicate groups (largest size on disk is the main file, every other location counts). Shown in Duplicates and Overview.
3. **Rich compare** — in Duplicates, a before/after slider for images, side by side Quick Look for everything else.
4. **Space map** — a new *Space* tab with a squarified treemap of one root (blocks proportional to size, drill into folders, duplicate bytes highlighted).
5. **Exclusions per set** — folders/files (relative paths) the set never touches, in every root. Excluded paths are removed from the sync memory before planning so they can never become pending deletions. A picker lists the folders found by the last scan.
6. **Automatic sync** — per set: *Off* or *When something changes* (FSEvents, debounced). An automatic run does exactly what a plan does without the confirmation: adds, copies, renames. It **never** removes anything; deletions stay in the review queue. Any root problem (missing, empty-but-had-files, different disk) skips the run and is shown, never forced.
7. **Schedule and notifications** — per set: *every 15 min / 30 min / hour / 6 hours* and *when a disk is mounted*; a local notification when an automatic run changed something or needs attention.
8. **Menu bar item** — status, last run, *Sync Now*, pause/resume of all automatic runs.

Out of scope (author's decision): exportable dry-run plan, Developer ID signing and notarization.

## 3. Approaches considered

- **A. Everything in the app target.** Fast, but the new rules (reclaimable bytes, treemap layout, exclusions, automation policy) would be untestable without UI.
- **B. Pure logic in `GTSyncCore`, thin SwiftUI on top (chosen).** Treemap layout, space aggregation, reclaimable bytes, exclusion filtering, automation settings and the "may this run now" policy are pure and tested; FSEvents lives in the package behind the existing `RootWatcher` protocol.
- **C. Separate helper/login item for automation.** Right for a store-grade background agent, but it adds a second target and sandbox work; the menu bar item inside the app is enough for now.

## 4. Decisions (builder's calls)

- `ExecutionEvent` gains `operation: SyncOperation` (source compatible: the old initializer stays).
- Automatic runs and manual runs never overlap (`isBusy` covers both); a trigger that arrives while busy is remembered once and replayed.
- Automation settings are stored with the set (`SyncSet.automation`, optional in JSON so old files load).
- Automation only runs while the app is running (menu bar item keeps it reachable); launch at login is not part of this change.
- An automatic run is skipped if the plan has nothing to do, so it stays silent.
- Exclusions match a path or anything below it, using the same case/accent-insensitive key as the rest of the engine.
- Visual match was not verified on screen (no display was available while building).
