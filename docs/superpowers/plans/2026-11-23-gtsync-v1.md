> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build GT Sync v1: a sandboxed macOS SwiftUI app that merges 2+ directories circularly (never overwriting, honoring intentional deletions through a review queue), with a duplicates area, previews, and a Liquid Glass UI.

**Architecture:** A local Swift package `GTSyncCore` holds the engine (scan, hash, snapshot, pure planner, executor, duplicate index, `SyncEngine` facade) and is fully unit-tested with temporary directories. The app target `GTSync` is a thin SwiftUI layer (`@Observable` models, `NavigationSplitView`, inspector, Quick Look) that calls `SyncEngine`.

**Tech Stack:** Swift 6.x (strict concurrency), SwiftUI, CryptoKit (SHA-256), Swift Testing, Quick Look (`QuickLookUI`), security-scoped bookmarks, Xcode 27.x, macOS 26 minimum.

**Spec:** `docs/superpowers/specs/2026-11-23-gtsync-design.md` and `docs/superpowers/specs/2026-11-23-gtsync-gui-design.md`

## Global Constraints

- Deployment target macOS 26.0; SwiftUI only; no UIKit/iOS code; Swift 6 language mode.
- App Sandbox + Hardened Runtime on from day one; folders accessed only through security-scoped bookmarks; entitlements: `com.apple.security.app-sandbox`, `com.apple.security.files.user-selected.read-write`, `com.apple.security.files.bookmarks.app-scope`.
- Merge only: a sync never overwrites or permanently deletes. Removals use `FileManager.trashItem`.
- Suffix naming: `name-1.ext`, `name-2.ext`, … ; add only if the hash differs from the same-named file and all its suffixed variants.
- Ignore: `.DS_Store`, `._*`, `.Trash`, `.Trashes`, `.Spotlight-V100`, `.fseventsd`, `.TemporaryItems`. Packages and symlinks are opaque single items.
- An unmounted/unreachable root aborts the sync for that set; absence is never a deletion.
- "Main" file of a duplicate group is the one with the largest size on disk (allocated size, `totalFileAllocatedSizeKey`, not logical size); ties: shortest path, then oldest modification date, then alphabetical path. All other members are "duplicates" and what happens to them is always the user's decision.
- All documentation, comments, identifiers and source UI strings in American English; Italian via String Catalog.
- Every new file carries `(c)Copyright 2026 by Gennaro Eduardo Tangari.`; every Swift file starts with the header from `CLAUDE.md` (file name, creation date, last-update date, copyright 2026). Update "Last update" on every edit.
- Product name shown to users: "GT Sync". App tint: blue-teal. Liquid Glass on chrome only, never on content, never glass on glass (consult the `liquid-glass` skill for current APIs).

## Review Focus

Spec silences most likely to bite a real user; each has a test in the owning task:

1. **Ghost mount:** `/Volumes/Backup` exists as an empty folder because the disk is not mounted. A mounted-but-empty root with a non-empty snapshot must abort, not read as mass deletion (Task 5).
2. **Case and Unicode names across volumes:** `Report.pdf` vs `report.pdf`, NFC vs NFD names from APFS vs exFAT must be one name, not two files (Tasks 2 and 6).
3. **File edited in place:** the new content becomes a `-x` copy and the old version survives; the old file is never overwritten (Task 6).
4. **Interrupted copy or full disk:** no partial file may ever appear under its final name; a rerun finishes the job (Task 9).
5. **Unreadable files and over-long names:** permission-denied items are skipped and reported without failing the sync; a suffix must not push a name past 255 bytes (Tasks 3 and 9).

### Task 6: Planner — merge, suffix variants, canonical naming

**Files:**

**Interfaces:**

  - `enum CopyReason: Sendable, Equatable { case add, variant }`

Canonical naming rule (builder's call, flagged to the user): for a name family (directory + base name + its `-x` variants), collect the distinct hashes. Same hash under different base names stays as is (both kept, per the spec decision).

### Task 7: Planner — renames and pending deletions

**Files:**
- Modify: `Planner.swift`; Test: `PlannerDeletionTests.swift`

**Interfaces:**
- Consumes: `Snapshot` entries (path → hash). Produces: renames and `PendingDeletion`s inside `SyncPlan` (types from Task 6).

Rules: a snapshot path P missing in root R, with R reachable:
- if R has a new path Q (not in the snapshot) with the same hash → `rename` P→Q in every other root that still holds P with that hash; roots without P receive a copy named Q;
- else, if other roots still hold P with the same hash → `PendingDeletion` (and no copy back into R);
- if another root changed P's content → not a deletion; ordinary merge (Task 6 behavior).
Pending paths are excluded from all copy operations.

### Task 10: SyncEngine facade and end-to-end convergence

**Files:**
- Create: `SyncEngine.swift`, `RootWatcher.swift`; Test: `SyncEngineTests.swift`

**Interfaces:**
- Consumes: everything above.
- Produces:
  - `struct ScanSnapshot: Sendable { let indexes: [RootIndex]; let issues: [ScanIssue] }`
  - `enum SyncError: Error, Sendable { case rootProblem(RootProblem) }`
  - `enum DeletionResolution: Sendable { case propagate, restore }`
  - `actor SyncEngine { init(set: SyncSet, store: SnapshotStore, ignore: IgnoreRules = .standard); func scan() async throws -> ScanSnapshot; func plan(_ scan: ScanSnapshot) async throws -> SyncPlan; func duplicates(_ scan: ScanSnapshot) -> [DuplicateGroup]; func execute(_ plan: SyncPlan, scan: ScanSnapshot, progress: @Sendable @escaping (ExecutionEvent) -> Void) async throws -> ExecutionReport; func resolve(_ pending: PendingDeletion, as: DeletionResolution) -> [Operation] }`

`scan()` runs `RootGuard.check` for every root first and throws `SyncError.rootProblem` before touching anything. `execute` runs `Executor`, then saves a new snapshot: the merged state (path → hash) from the post-run re-scan, **keeping entries of unresolved pending deletions** so they reappear next time. `resolve(.propagate)` → `.trash` in `presentIn`; `.restore` → `.copy` from a `presentIn` root to each `deletedIn` root.
